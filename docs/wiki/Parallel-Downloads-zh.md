# 并行下载

[English](Parallel-Downloads) · **中文**

当一个任务拿到多于 1 条连接、且服务端支持 Range 请求时，文件会被并行取回。这一页说明文件怎么切分、切片长度怎么定。

## 两个层次：粒度与切片

引擎**不预先**把文件切成固定分片。预切会在开头就把连接数和分片边界都定死，而这恰恰是[动态分配](Scheduling-and-Budget-zh)必须保持灵活的东西。

所以分成两层：

- **粒度（granule）**：64 KiB，完成度位图的分辨率。10 GB 文件只需要 20 KB 位图。
- **切片（piece / block）**：一个 worker 一次认领的长度，是粒度的整数倍，在认领那一刻决定，因此可以随时变化而不扰动位图。

worker 循环执行：

1. 认领下一段连续空闲粒度；
2. 对这段字节区间发一个带 Range 的请求；
3. 按偏移写入响应体；
4. 标记这些粒度已完成。

被放弃的认领 —— 暂停、请求失败 —— 只需清掉自己的位。那段之后会被重新取，而同一区间里另一个 worker 已经写完的字节不会丢。

## 为什么进度按已完成片计数

`Progress().Downloaded` 只统计**已经可靠落盘**的字节：写入并标记完成的粒度。在途未写完的不计入。

代价是进度会比实际传输滞后，上界是每条连接一片。收益是暂停时**完全不需要补偿计算**，续传也不依赖服务端响应 `If-Range`：位图是「磁盘上有什么」的唯一事实来源。

## 切片长度怎么定

- **第一片**是 `文件大小 / (连接数 × 4)`，夹在 `[256 KiB, 16 MiB]`。每连接 4 片意味着很少出现「一个 worker 没活干而另一个还在忙」。
- **运行中**，用每一片的**实测耗时**把长度朝「每片约 1.5 秒」的目标拉。每次调整幅度不超过一倍，且结果不越出配置的上下界，所以一次异常响应不会让切片崩掉或爆掉。
- **收尾时**，把剩余字节按连接数分给各 worker，让它们一起结束，而不是留下一个 worker 磨最后一大段。

要固定长度并关闭自动调整：

```go
muyuan.WithChunkSize(512 << 10)       // 一片恒为 512 KiB
muyuan.WithChunkBounds(64<<10, 8<<20) // 或者只改上下界
```

## 什么时候不会并行

以下情况会跳过并行、改用单连接取整个文件：

- 任务只被分配到**1 条连接**（见[调度](Scheduling-and-Budget-zh)）；
- 服务端对 Range 请求返回 **200 而不是 206**，即它忽略 `Range`；
- 服务端**不报告文件大小**，没有可切分的东西；
- 文件**小于两倍最小切片**（默认 512 KiB）。切这么小的文件，开销大于收益。

第一种情况最常见：默认预算 4、三个文件时，每个文件只拿到 1 条连接。

具体是哪种情况，看 `task.RangeMode()`：

| 值 | 含义 |
| --- | --- |
| `RangeUnknown` | 还没有 Range 请求被回应过 |
| `RangeSupported` | 服务端支持 Range，可以并行取片 |
| `RangeUnsupported` | 服务端忽略 `Range`，中断的传输只能从头再来 |

注意「单连接 + `RangeSupported`」是正常的：它表示服务端**有能力**支持 Range，而不是说这次传输正在用。

## 分片模式下 `.part` 会被创建成完整大小

并行路径会把 `.part` 文件**预先创建成整个文件的大小**，再用定位写入原地填充。两个后果：

- **暂停时 `.part` 的文件大小是整个文件的大小**，不是已下载量。判断进度请用 `Progress().Downloaded`，不要看文件大小。
- 在**不支持稀疏文件**的文件系统上，传输开始时就会真实占用完整大小的磁盘空间。

单连接路径下 `.part` 大小就是已接收量，符合直觉。两种模式里 `Downloaded` 的含义一致。
