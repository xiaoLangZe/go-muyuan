# 设计原理

[English](../../doc/ARCHITECTURE.md) | **中文**

本文说明 `go-muyuan` 如何完成一次下载、磁盘布局为何如此设计，以及运行时热重配为什么是安全的。

术语（完整对照表见 README）：一条**连接（connection）**是一次 HTTP 传输；一个**切片（segment）**是文件的一段字节区间；**Workers** 是（连接 + 切片）的总和预算，由库自动分配两者；**并发（concurrency）**指队列同时下载多少个*文件*。

## 总览

一个 `Downloader` 持有一个 `manager`。manager 在每次 `Start` 时创建，并在单个 goroutine 中运行，负责：

1. **探测**服务端（一次 `HEAD`，再补一次 1 字节的 `Range` GET），获知总大小、`ETag`、`Last-Modified`，以及是否支持 `Accept-Ranges`。
2. **核对**磁盘上的进度与探测到的资源是否一致（续传，或丢弃重来）。
3. **构建切片计划**——把文件切分成若干连续的字节区间。
4. **运行连接池**：T 个 goroutine 反复认领下一个未完成的切片，下载其剩余字节。
5. **响应控制信号**（暂停/继续/重配/重下/清缓存/停止/中止）。

## 连接与切片

两个独立的旋钮：

- **切片（`Segments`）** —— 文件被划分成多少个字节区间。它决定计划的长度，同时决定续传粒度。
- **连接（`Connections`）** —— 同时有多少条连接在运行。每条连接同一时刻最多持有一个切片。

连接认领一个切片，下载 `[Start+Downloaded, End)`，标记完成，再认领下一个。当切片数多于连接数时，连接会**复用**自己去处理后续切片；实际并行度为 `min(Connections, 未完成切片数)`。

这也解释了为什么 `Connections > Segments` 没有意义——总共只有 `Segments` 块要抓，多出来的连接立刻就会空闲。

## 磁盘布局

对于输出路径 `P`：

| 路径 | 用途 |
| --- | --- |
| `P` | 最终文件（仅在成功时生成） |
| `P.muyuan.partial` | 进行中的文件，已按完整大小预分配 |
| `P.muyuan.meta.json` | JSON 进度记录 |

元数据记录 URL、大小、`ETag`、`Last-Modified`、连接数（仅作参考），以及每个切片的
`{position, start, end, downloaded}` 数组。切片*数量*就是该数组的长度——刻意不另设
计数字段，避免两处状态不一致。

### 为什么用单个临时文件（而不是每片一个 part 文件）

一种朴素的做法是把每个切片写进各自的 `P.partN` 文件，最后再拼接。这让重切片变得昂贵：改变切片数就得读取并重写所有 part。

本包的做法相反：所有切片共享**同一个**临时文件，每条连接把字节写到该切片在文件中的**绝对偏移**处（通过 `WriteAt`）。一个字节在文件里的位置与"它属于哪个切片"无关。由此带来：

- **没有合并步骤。** 完成时只需 `fsync` + `rename`。
- **重切片只动元数据。** 改变切片边界只需重算各切片的 `downloaded` 计数；没有任何字节需要搬运。

元数据的写入是原子的（序列化 → 临时文件 → `rename`），因此写入中途崩溃也不会破坏记录。

## 续传

`Start` 时若 `P.muyuan.meta.json` 存在，会拿它与刚探测到的资源核对：

- 大小必须一致（双方都已知时），
- `ETag` 必须一致（双方都存在时），
- `Last-Modified` 必须一致（双方都存在时）。

任何不一致都会丢弃进度、从头开始，避免把一份半旧的文件与新字节拼在一起。若一致，则跳过已完成的切片，未完成的切片从 `Start+Downloaded` 继续。

## 运行时热重配

重配置是最微妙的部分。让它安全的那条规则是：

> **一代连接在运行期间绝不被改动。** 要改变任何东西，manager 会先取消当前这一代，等待**每一条**连接返回，然后才重建计划并拉起新的一代。

`runExclusive` 实现了这一点：若有连接在运行，它会把变更排队并取消它们；当该代报告结束后，manager 再执行排队的变更。暂停、重配、重下、停止、清缓存统统走这条路径。

### 重切片通过「连续前缀」保留进度

当切片数变化时，`reinterleave` 会从旧计划重算每个新切片的 `Downloaded`。关键细节是：它使用的是磁盘上已存在的**最长连续前缀**，而不是区间交集总量。

为什么这一点重要：当旧、新边界不对齐时，某段已下载区域可能落在新切片内部某个空洞**之后**。以 200 字节的文件为例：

```text
旧切片:   [0,100) 已完成          [100,200) 已完成 50 字节
旧区间:   [0,100)                [100,150)
新切片:   [0,200) 横跨两者
交集总量 = 150   ✗  从 150 续传，跳过了 [50,100) 这段字节
连续前缀 = 100   ✓  从 100 续传，重新抓取 [100,200)
```

使用连续前缀能保证连接续传的位置之前的所有字节都是有效的。落在空洞之后的字节会被重新下载——这是安全的；聚合的 `Downloaded` 计数会依据新计划重新推导，因此进度上报保持诚实。

### Workers 总和分配

`Config.Workers` 是（连接 + 切片）的总预算。当它非零时，`allocateWorkers` 推导出 `Connections`（约 `Workers/3`，钳制在 `[2, 64]`），并把 `Segments` 留 `0`（自动），由切片计划构建器挑选一个让每条连接始终有段可领的切片数。这是推荐的高性能模式：调用方只设一个数，库自行决定切分。`Workers` 设 `0` 则回退到传统分别设置模式，`Connections` 与 `Segments` 各自独立设置，两者都保留可用。

### 慢分片自动拆分

在 Workers 模式下（以及传统模式下同样）manager 会周期性运行慢分片检测器（`maybeSplitSlowSegments`，每约 2 秒一次）：

1. 采样每个进行中分片自上次以来的字节/秒增量。
2. 计算所有进行中分片速率的中位数。
3. 速率低于 `中位数/2` **且**剩余 `≥ 2 × MinSegmentSize` 字节的分片被拆分：其剩余范围的后半段成为一个新分片，释放其领取权，使更快的 worker 可以立即认领。

拆分是纯元数据操作——所有分片共享同一个 partial 文件、字节按绝对偏移写入，因此新增边界不搬运任何数据。当前连接继续从停止处下载前半段；新分片从拆分点起、`Downloaded = 0`。

这就是"一个切片下载速度慢时自动分割切片、以最高性能下载"的实现，且全程不复制字节。

## 降级：不支持 Range

若服务端对 `Range` 请求不返回 `206 Partial Content`（或长度未知），下载就无法切片、也无法续传。此时 manager 会切换为**单个顺序切片**，由一条连接从偏移 0 开始流式拉取整个响应体。已有的进度会被丢弃，因为它无法被校验。

## 队列（批量下载）

`Queue` 负责调度许多个 `Downloader`。它把两个维度分开：

- **`Concurrency`** —— 同时有多少个文件处于活动状态（队列级）。
- **`Connections` / `Segments`** —— 上文所述的每文件旋钮。

一个调度器 goroutine 独占全部队列状态，运行一个小循环：处理信号 → 重算调度计划 →
执行计划 → 检查是否完成。所有状态变更都在这一个 goroutine、同一把互斥锁下发生；
而阻塞型工作（创建 `Downloader`、探测服务端、等待下载结束）都在每个任务自己的
runner goroutine 中进行，绝不在持锁时执行。

### 挂起会释放槽位

这里有一个微妙但必要的要求：挂起一个任务时，**不能**让一条空闲连接继续占着并发槽位——否则大批量场景会卡住，槽位全被"没人要求运行"的任务占据。

这就是队列用**停止（Stop）**任务下载器来挂起的原因（它会退出 manager 并把进度落盘），而不是调用 `Downloader.Pause`（那会让 manager 常驻）。槽位被释放、进度在磁盘上，恢复时创建一个新的 `Downloader`，从 sidecar 继续。

两种暂停不能混淆：

- **队列挂起**（`Pause`，或调低 `Concurrency`）是*可恢复*的：有空槽时任务会重新变为可调度。
- **调用方暂停**（`PauseTask`）是*粘性*的：队列 `Resume` 不会唤醒它。内部就是一个
  `userPaused` 标记，在判断"暂停中的任务是否可运行"时被参考。

把 `Concurrency` 调到低于当前运行数时，**最近启动**的任务会被挂起，从而让"最接近完成"的那些继续跑。

### 重试与永久性故障

失败的尝试会在**队列层**重试（最多 `MaxRetries` 次，间隔 `RetryDelay`），做法是重新启动该任务；新的 `Downloader` 会从 sidecar 续传，所以重试不会从头再来。

在单个文件内部，`retrySegment` 会对瞬时故障做有上限的退避重试。它刻意**不**重试 `permanentError`——`statusError` 对 4xx 响应（408 与 429 除外）会返回该类型。没有这一点，一次 404 会先耗光整个退避预算（约 3.5 秒）才失败，既慢又无意义。5xx 仍可重试。

### 推导输出路径

未显式指定 `OutputPath` 的任务，其文件名从 URL 推导。推导只取路径最后一段，并剥离目录分隔符、控制字符以及文件系统保留字符，因此构造过的 URL 无法逃出 `OutputDir`。重名会与已有任务比对，通过追加 `-1`、`-2` 等去重。

### 任务错误

`Queue.Wait` 把所有任务失败聚合为一个由 `*TaskError` 组成的 `errors.Join`，每个都带任务 ID 与 URL。全部成功的队列返回 nil；只要有一个失败就返回非 nil——即使其他任务已完成，部分失败也不会被静默吞掉。`Summary` 提供明细。

## 错误模型

- 真正的 worker 错误会让整个下载失败（`StateFailed`，`Wait` 返回该错误）；而主动取消会被报告为 `nil`，这样 manager 才能把两者区分开。
- 单个切片内部的瞬时故障会用有上限的指数退避重试（`retrySegment`）；取消从不重试，永久性 HTTP 状态同样不重试。
- 重试会依据当前状态重算续传偏移，因此部分失败后的重试是"继续"而不是"重写"。

## 并发不变式

- `manager.mu` 守护计划、认领状态、计数器与状态机。
- 生命周期字段（`exit`、`genRunning`、`cancelGen`、`afterGen`）由 manager goroutine 独占；连接绝不触碰它们。
- 连接与 manager 之间通过计划（互斥锁守护）和每代的 `genDone` 通道通信。该通道提供了 happens-before 关系，使得 manager 只有在所有连接都返回之后，才会安全地关闭/重命名临时文件。
- 锁序是单向的（`Queue.mu` → `manager.mu`）；进度回调在释放内层锁之后才被调用，因此不存在反向获取的路径。
