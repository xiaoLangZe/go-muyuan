# 架构设计

本文解释 `go-muyuan` 如何完成一次下载、磁盘布局为什么是这样，以及热重配为什么安全。

术语回顾（完整表见[简介](./introduction)）：**连接**是一次 HTTP 传输，**切片**是文件的一段字节区间，**workers** 是库自动分配的（连接 + 切片）总和预算，**并发**是队列同时下载多少个*文件*。

## 总览

一个 `Downloader` 拥有一个 `manager`。manager 在每次 `Start` 时创建，run 在单个 goroutine 中：

1. **探测**服务端（`HEAD`，再一个 1 字节 `Range` GET），获知总大小、`ETag`、`Last-Modified`，以及是否支持 `Accept-Ranges`。
2. **核对**磁盘上的既有进度与探测结果（续传或丢弃）。
3. **构建切片计划**——把文件切成连续字节区间。
4. **运行连接池**：T 个 goroutine 反复认领下一个未完成切片并下载其剩余字节。
5. **响应控制信号**（暂停/继续/重配/重下/清缓存/停止/中止）。

## 连接 vs 切片

两个独立旋钮：

- **切片（`Segments`）**——文件被切成多少段字节区间。它同时决定计划长度与续传粒度。
- **连接（`Connections`）**——同时运行多少条连接。每条连接同一时刻最多持有一段。

一条连接认领一段，下载 `[Start+Downloaded, End)`，标记完成，再认领下一段。切片数多于连接数时，连接会**复用**——实际并行度是 `min(Connections, 未完成切片数)`。

这就是 `Connections > Segments` 没有意义的原因：只有 `Segments` 段可取，多出的连接会立即空转。

## 磁盘布局

对输出路径 `P`：

| 路径 | 用途 |
| --- | --- |
| `P` | 最终文件（仅在成功时创建） |
| `P.muyuan.partial` | 下载中的文件，预分配到完整大小 |
| `P.muyuan.meta.json` | JSON 进度记录 |

元数据记录 URL、大小、`ETag`、`Last-Modified`、连接数（仅供参考），以及每段的 `{position, start, end, downloaded}` 数组。切片**数量**就是数组长度——刻意不设独立的计数字段，避免两者漂移不一致。

### 为什么用单个 partial 文件（而不是每段一个 part 文件）

朴素做法把每段写到自己的 `P.partN`，最后拼接。这让重切片变得昂贵：改切片数需要读写每个 part。

本库让所有切片共享**同一个** partial 文件，每条连接通过 `WriteAt` 把自己的字节写到该段的**绝对偏移**。一个字节在文件中的位置与它属于哪一段无关。由此得到：

- **没有合并步骤。** 完成就是 `fsync` + `rename`。
- **重切片只是改元数据。** 改段边界只需重算每段的 `downloaded` 计数，不搬字节。

元数据写入是原子的（marshal → 临时文件 → `rename`），写入中途崩溃不会损坏记录。

## 续传

`Start` 时，若 `P.muyuan.meta.json` 存在，会与刚探测到的资源核对：

- 大小必须一致（双方都已知时），
- `ETag` 必须一致（双方都存在时），
- `Last-Modified` 必须一致（双方都存在时）。

任何不一致都会丢弃进度并重新开始，防止把半旧文件与新字节拼在一起。兼容时，已完成的切片跳过，未完成的切片从 `Start+Downloaded` 继续。

## 热重配

重配是最微妙的部分。让它安全的规则只有一条：

> **连接代次在运行期间绝不被修改。** 要改任何东西，manager 先取消当前代次，等**每一条**连接返回，然后才重建计划并生成新一代。

`runExclusive` 实现这一点：若有连接在运行，它把变更排队并取消连接；manager 在该代次报告完成后应用排队的变更。暂停、重配、重下、停止、清缓存都走这条路径。

### 重切片通过*前缀*覆盖保留进度

切片数变化时，`reinterleave` 从旧计划重算每个新切片的 `Downloaded`。关键细节是它采用磁盘上已存在的**最长连续前缀**，而不是总交集。

为什么重要：当新旧边界不对齐时，已下载区域可能落在新切片内部的一个"洞"之后。以 200 字节文件为例：

```text
old segments:  [0,100) done            [100,200) 50 bytes done
old ranges:    [0,100)                 [100,150)
new segment:   [0,200) spanning both
intersection = 150   ✗  resumes at 150, skipping bytes [50,100)
prefix       = 100   ✓  resumes at 100, re-fetching [100,200)
```

用前缀可以保证连接的续传偏移之前的所有字节都是有效的。洞之后的零散字节会被重新下载，这是安全的；聚合的 `Downloaded` 计数从新计划重新推导，所以上报仍然诚实。

### Workers 总和分配

`Config.Workers` 是（连接 + 切片）的总预算。非零时，`allocateWorkers` 推导出 `Connections`（约 `Workers/3`，钳制到 `[2, 64]`），并把 `Segments` 留作 `0`（自动），于是计划构建器会选一个让每条连接都忙的切片数。这是推荐的高性能模式：调用方给一个数，库自己决定切分。`Workers` 设为 `0` 则回到传统的分旋钮模式。

### 自适应慢分片拆分

在 Workers 模式（以及传统模式）下，manager 运行一个周期性的慢分片检测器（`maybeSplitSlowSegments`，约每 2 秒）：

1. 采样每个在途切片自上次采样以来的字节/秒。
2. 计算所有在途切片速率的中位数。
3. 速率低于 `中位数/2` **且**剩余字节 `>= 2 * MinSegmentSize` 的切片会被拆分：其剩余区间的后半段成为新切片并释放认领，让更快的 worker 能立即接手。

拆分是纯元数据操作——所有切片共享一个 partial 文件，字节按绝对偏移写入，因此划出新边界不移动任何数据。当前连接从前半段停下的位置继续；新切片从拆分点开始，`Downloaded = 0`。

## 降级：不支持区间请求

若服务端对 `Range` 请求不返回 `206 Partial Content`（或长度未知），下载就无法拆分或续传。manager 会切换为**单个顺序切片**，由一条连接从偏移 0 流式拉取整个 body。既有进度会被丢弃，因为无法验证。

## 队列（批量下载）

`Queue` 调度多个 `Downloader`，它把两个维度分开：

- **`Concurrency`**——同时有多少个文件活跃（队列级）。
- **`Connections` / `Segments`**——上面各节的每文件旋钮。

单个调度 goroutine 拥有全部队列状态，跑一个小循环：处理信号、重算计划、应用、检查完成。所有状态变更都在该 goroutine 上、单个互斥锁保护下进行；阻塞性工作（创建 `Downloader`、探测服务端、等待下载）发生在每任务的 runner goroutine 中，绝不在持锁时进行。

### 挂起会释放槽位

微妙的要求是：挂起一个任务不能留下一条空闲连接占着并发槽位——否则大批量会在所有槽位被"没人要求运行"的任务占满时停滞。

因此队列挂起是通过**停止**任务的 downloader（退出 manager 并持久化进度）实现的，而不是 `Downloader.Pause`（那会让 manager 继续存活）。槽位被释放，进度在磁盘上，继续时创建新的 `Downloader` 从 sidecar 续传。

两种暂停必须区分：

- **队列挂起**（`Pause`，或调低 `Concurrency`）是*可恢复*的：槽位空出时任务重新可运行。
- **调用方暂停**（`PauseTask`）是*粘性*的：队列 `Resume` 不会唤醒它。内部就是一个 `userPaused` 标志，在判断暂停任务是否可运行时查。

把 `Concurrency` 调到低于运行数时，挂起**最近启动**的任务，让最接近完成的任务继续跑。

### 重试与永久失败

失败的尝试在队列层面重试（最多 `MaxRetries` 次，间隔 `RetryDelay`）——重新启动任务；新的 `Downloader` 从 sidecar 续传，所以重试不会重新开始传输。

单文件内部，`retrySegment` 对瞬时故障做有界退避重试。它**刻意不重试** `permanentError`——`statusError` 对 4xx（除 408 和 429）返回它。否则一个 404 会先耗尽整个退避预算（约 3.5 秒）才失败，既慢又无意义。5xx 保持可重试。

### 派生输出路径

没有显式 `OutputPath` 的任务，其名字从 URL 派生：只取最后一个路径段，剥掉目录分隔符、控制字符与文件系统保留字符，因此构造过的 URL 无法逃出 `OutputDir`。重名通过追加 `-1`、`-2` 去重。

### 任务错误

`Queue.Wait` 返回所有任务失败的聚合，为 `errors.Join` 的 `*TaskError`，各带任务 ID 与 URL。全部成功的队列返回 `nil`；有任何失败的队列返回非 nil（即使其他任务成功），因此部分失败不会静默通过。`Summary` 给出分类。

## 错误模型

- 真正的 worker 错误会让整个下载失败（`StateFailed`，`Wait` 返回错误）；主动取消上报为 `nil`，以便 manager 区分两者。
- 切片内的瞬时故障按有界指数退避重试（`retrySegment`）；取消从不重试，永久性 HTTP 状态也不重试。
- 重试会从当前状态重算续传偏移，所以部分失败后的重试是继续而不是重写字节。

## 并发不变量

- `manager.mu` 保护计划、认领、计数与状态。
- manager goroutine 拥有生命周期字段（`exit`、`genRunning`、`cancelGen`、`afterGen`）；连接从不触碰它们。
- 连接与 manager 通过计划（互斥保护）和每代次的 `genDone` channel 通信，后者提供 happens-before 边，使 manager 只能在所有连接返回后才安全地关闭/重命名 partial 文件。
- 锁顺序单向（`Queue.mu` → `manager.mu`）；进度回调在释放内层锁之后调用，因此没有任何路径以相反顺序取锁。
